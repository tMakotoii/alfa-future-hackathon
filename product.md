# Product: «Альфа Инсайт» — персонализированная новостная аналитика для крупного бизнеса

> Рабочий продуктовый документ для хакатона «Альфа-Будущее» (кейс Changellenge × Альфа-Банк).
> Источник требований: `CASE.pdf`. Данные: `data/`.
> Документ описывает **что** и **зачем** строим. **Как** — уточняется на этапе brainstorming/design.

---

## 1. Проблема и цель

Руководители крупного бизнеса (выручка > 15 млрд ₽) ежедневно принимают решения под влиянием внешних факторов:
ключевая ставка, инфляция, курсы, сырьё, регулирование, действия конкурентов и контрагентов.
У них уже есть свои аналитики и новостные ресурсы — **сама новость им не нужна, нужно понимание, как событие
повлияет на их компанию**.

**Цель:** сервис внутри интернет-банка Альфа-Бизнес, который:
1. понимает бизнес-контекст конкретной компании (и её группы);
2. отбирает из потока новостей и аналитики Альфа-Банка значимые для неё события;
3. объясняет их влияние: риски, возможности, позиция банка, возможные действия;
4. каждый вывод связывает с первоисточником и явно разделяет «факт / мнение банка / вывод AI».

**Чем продукт НЕ является:** новостной лентой и AI-пересказчиком новостей. Если интерпретацию можно
получить, прочитав только заголовок, — это провал.

## 2. Пользователи

Пользователь — **человек**, а не юрлицо. У одной компании может быть несколько пользователей с разными ролями.

| Роль | Что для него важно (гипотеза) |
|---|---|
| Собственник / CEO | стратегия, рынок, конкуренты, M&A, регулирование отрасли |
| Финансовый директор | ставка, стоимость долга, ликвидность, курсы, рефинансирование |
| Казначей | курсы, ставки по депозитам/облигациям, размещение свободной ликвидности |
| Главный бухгалтер | налоги, отчётность, изменения регулирования, ВЭД/таможня |
| Иной C-level / ЛПР | новости по своему направлению (закупки, логистика, HR) |

**Требование:** роль пользователя влияет на ранжирование и на акценты интерпретации одной и той же новости.

## 3. Ключевой пользовательский сценарий (E2E)

1. Пользователь входит в интернет-банк Альфа-Бизнес (тестовая учётка), видит главный экран.
2. На главном экране — **заметная, постоянно доступная точка входа** в сервис (виджет «Что важно для вашего бизнеса сегодня» с 2–3 топ-инсайтами).
3. Переход в ленту инсайтов: события отранжированы по значимости **для этой компании и этой роли**,
   у каждого — короткое «почему это важно вам» и метка влияния (риск / возможность / нейтрально).
4. Открытие карточки события — полная интерпретация по 6 вопросам (раздел 5).
5. Пользователь задаёт уточняющий вопрос в чате по событию («а как это повлияет на наш лизинг?»),
   просит другой разрез («покажи по контрагентам»), переходит к первоисточнику.
6. Видит следующее действие (если обосновано): например, обсудить рефинансирование с менеджером,
   хеджирование, депозит — нативная интеграция продуктов банка.
7. Может раскрыть «Как получен вывод» — трассу агента: шаги, использованные источники,
   признаки компании, повлиявшие на вывод.

**Демо-требование:** переключение между 2–3 разными клиентами показывает, что лента и интерпретации
**реально меняются**. Работает на «живых» новостях, не показанных заранее.

## 4. Функциональные модули

### F1. Профиль компании (бизнес-контекст)
Из данных `df_Uid_data_hack.csv` + связи + платежи строим профиль:
- отрасль (ОКВЭД → отраслевая группа → чувствительность к макрофакторам);
- масштаб: выручка, численность, возраст, стадия развития;
- группа компаний (`GROUP_ID`): совокупная выручка, состав, отрасли участников;
- банковские продукты: кредиты, лизинг, гарантии, депозиты, ЗП-проект, факторинг → **финансовая чувствительность**
  (кредиты → ставка; депозиты → ставка как доход; ФТС → курсы, ВЭД, санкции, таможня);
- контрагенты из платежей: ключевые поставщики и покупатели, их отрасли, концентрация;
- регион/город присутствия;
- позиция в отрасли и доля рынка (оценка внутри датасета — это приблизительно, должно быть явно помечено).

Профиль = структурированный JSON с **признаками и их происхождением** (из какого поля/расчёта).
Должен корректно работать при пропусках (см. раздел 8).

### F2. Сбор и обработка материалов
- **Внешние новости:** парсер из открытых источников (RSS/сайты: ЦБ РФ, Интерфакс, РБК, ТАСС, Минфин,
  отраслевые СМИ — выбрать доступные и легальные). Регулярный сбор + ручная загрузка новости/URL для демо.
- **Аналитика Альфа-Банка:** 9 PDF из `data/Аналитические материалы/` (OCR → чанки → индекс).
- Обработка: очистка, дедупликация/кластеризация одного события из разных источников,
  классификация (тема, отрасли, макрофакторы, регионы, компании), извлечение ключевых фактов
  (что, кто, когда, цифры), тональность.

### F3. Отбор и ранжирование
Сопоставление события с профилем компании → оценка значимости с объяснимыми компонентами, например:
отраслевое совпадение, совпадение по контрагентам, финансовая чувствительность (продукты), регион, роль
пользователя, свежесть, подтверждённость, наличие позиции банка. Результат — score + разбивка «почему».
Гибрид: быстрый правиловый/эмбеддинговый префильтр → LLM-реранкинг топа (экономия бюджета).

### F4. Персонализированная интерпретация (агент)
Многошаговый агент формирует инсайт по 6 вопросам (раздел 5), обязательно используя:
профиль компании, саму новость, связанные новости, релевантную аналитику Альфа-Банка (RAG).
Вывод должен учитывать **несколько факторов**, а не одно очевидное следствие.

### F5. Интерфейс (прототип Альфа-Бизнеса)
- Главный экран интернет-банка (упрощённый) с точкой входа.
- Лента инсайтов с фильтрами (риски/возможности, темы, период).
- Карточка события с визуальным разделением блоков: **Факт** / **Мнение Альфа-Банка** / **Вывод AI**.
- Чат для уточняющих вопросов в контексте события и компании.
- Панель трассировки «Как получен вывод».
- Выбор клиента и роли (для демо) / тестовые учётки.

### F6. Диалог с аналитикой
Уточняющие вопросы, другой разрез данных, переход к источнику. Тот же агент с тем же контекстом.

### F7. Наблюдаемость и качество
Журнал вызовов агента и инструментов, сбор обратной связи (👍/👎, «не релевантно», «неверно»),
метрики (раздел 10).

## 5. Формат качественного инсайта

Каждая интерпретация отвечает на 6 вопросов:

1. **Что произошло?** — факты, участники, сроки, причины; подтверждённое отдельно от предположений.
2. **Почему это важно для этой компании?** — связь с отраслью, продуктами, контрагентами, регионом, финансами.
3. **Какие последствия возможны?** — риски, возможности, факторы развития ситуации.
4. **Какие действия могут быть релевантны?** — конкретные направления, вопросы для анализа, сценарии (не общие слова).
5. **Как это оценивает банк?** — позиция Альфа-Банка из аналитики, явно помеченная.
6. **На чём основан вывод?** — ссылки на новости, аналитику банка, признаки клиента.

Эталон из кейса: ставка ЦБ 14% для компании с кредитами →
«период быстрого удешевления кредитов приостановлен, финансовая нагрузка не снизится», а не пересказ пресс-релиза.

### Набросок схемы данных инсайта (уточнить на design)
```json
{
  "insight_id": "...",
  "company_id": "U_...",
  "user_role": "CFO",
  "event": {"title": "...", "summary": "...", "facts": [{"text": "...", "source_id": "...", "confirmed": true}]},
  "relevance": {"score": 0.82, "factors": [{"name": "credit_products", "weight": 0.3, "evidence": "CL_PRODUCT_LOA_MARK=1"}]},
  "why_it_matters": [{"text": "...", "company_features": ["..."], "origin": "ai"}],
  "impacts": [{"type": "risk|opportunity", "text": "...", "horizon": "...", "confidence": "low|med|high", "origin": "ai|bank"}],
  "bank_view": [{"text": "...", "source_id": "alfa_policy_rate_11sep", "page": 2}],
  "actions": [{"text": "...", "product_link": "optional"}],
  "sources": [{"id": "...", "type": "news|bank_analytics|client_data", "url_or_ref": "..."}],
  "trace_id": "..."
}
```
Ключевое: у каждого утверждения есть `origin` (`fact` / `bank` / `ai`) и ссылки на источники.

## 6. Агентная логика (обязательное требование кейса)

Не однократная генерация, а многошаговый процесс:
- **Планирование:** агент определяет, какие данные и источники нужны, строит план шагов.
- **Инструменты:** `get_company_profile`, `get_counterparties`, `search_news`, `search_bank_analytics` (RAG),
  `get_related_events`, `compute_relevance` и т.п. — набор уточнить на design.
- **Контекст:** результаты шагов накапливаются в едином состоянии (компания + событие).
- **Самопроверка и адаптация:** проверка полноты, непротиворечивости, обоснованности
  (каждое утверждение имеет источник?), при недостатке — повторный поиск / уточнение / переписывание шага.
- **Трассируемость:** все шаги, вызовы и промежуточные результаты сохраняются и показываются в UI.

Логику агента пишем **сами** (без готовых агентных фреймворков/автономных агентов как основы).
Один агент с инструментами или несколько — решаем на design; число агентов не влияет на оценку.

## 8. Ограничения и нефункциональные требования

- **LLM только из списка:** Gemma 4 26B A4B (лёгкие задачи: классификация, извлечение), GLM-5.3-Flash (сложные
  рассуждения), Qwen3.6 35B A3B (универсальная), DeepSeek-V4.1-Flash (поиск связей, большие объёмы),
  Qwen3-VL-30B-A3B-Instruct (изображения), Kimi-K2.6 (текст). Других LLM и внешних AI-сервисов — нельзя.
- **Бюджет:** общий ключ, дневной лимит ≈ 500 ₽. → кэширование ответов, предрасчёт инсайтов в фоне,
  дешёвые модели для классификации, LLM только на топе после префильтра, учёт токенов.
  Эмбеддинги — локальная open-source модель (проверить, что это допустимо; указать в THIRD_PARTY_NOTICES).
- **Грязные данные:** пропуски, дубли, противоречия, шумные новости → деградировать мягко, явно помечать неуверенность.
- **Устойчивость:** работа на ранее не показанных новостях; никаких захардкоженных сценариев.
- **Безопасность AI (описать + показать место в архитектуре):** разграничение прав (пользователь видит только свою
  компанию/группу), маскирование чувствительных данных перед отправкой в LLM, allow-list инструментов,
  журналирование вызовов, защита от prompt injection из текста новостей, read-only инструменты.
- **Масштабируемость:** новые отрасли (конфиг отраслевых чувствительностей, а не код), новые источники
  (плагинные парсеры), новые типы клиентов.

## 10. Метрики качества (предложение)

- **Персонализация:** доля инсайтов, отмеченных пользователем как релевантные; precision@k ленты по экспертной разметке;
  различие лент между клиентами (overlap).
- **Контент:** доля утверждений с источником (groundedness), доля фактологических ошибок (проверка LLM-судьёй +
  выборочная экспертная), доля инсайтов с позицией банка, «глубина» (число учтённых факторов).
- **AI-компонент:** число итераций самопроверки, доля повторных поисков, латентность, стоимость инсайта в токенах/₽.
- **Процесс:** регулярный прогон золотого набора (company × news → ожидаемые признаки/выводы), сбор 👍/👎 и
  комментариев экспертов банка, дашборд метрик.

## 12. Скоуп

**MVP (обязательно к демо):** профиль компании + группы + контрагенты; парсер 2–3 источников + ручной ввод новости;
OCR-корпус аналитики банка + RAG; ранжирование с объяснением; агент с планированием, инструментами, самопроверкой
и трассой; UI: главный экран → лента → карточка → чат → трасса; переключение клиентов и ролей; Docker; README.

**Nice-to-have:** граф связей компаний (визуализация), дайджест по расписанию/уведомления, дашборд метрик качества,
фидбэк-цикл в ранжирование, деплой на внешний сервер, нативные продуктовые предложения.

## 14. Риски

- Бюджет токенов исчерпан во время демо → предрасчёт + кэш + fallback-модель.
- OCR-ошибки в цифрах аналитики банка → ручная проверка ключевых цифр, хранение ссылки на страницу.
- Галлюцинации → обязательная привязка утверждений к источникам + шаг самопроверки.
- Парсер блокируется сайтом → несколько источников + ручная загрузка + сохранённый снапшот.
- Слабая персонализация («всем одно и то же») → объяснимый score с компонентами, контрастные демо-клиенты.
